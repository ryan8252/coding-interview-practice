# Coding Interview 練習紀錄

這個 Repository 用來記錄我準備新鮮人 AI / Computer Vision / Software Engineering 職缺的 Coding Interview 練習進度。

## 訓練目標

建立扎實的程式基礎與常見題型的辨識能力，目標是：

- 常見 Easy 題可以在約 15～20 分鐘內獨立完成。
- 常見 Medium 題可以在約 30～40 分鐘內想出方法並完成。
- 面試時可以清楚說明自己的思路、時間／空間複雜度與不同解法的取捨。
- 定期重做不熟的題目，直到原本困難的題型變成熟悉的 Pattern。

## 評分方式

| 等級 | 定義 |
|---|---|
| A | 完全自己想出演算法並完成，沒有看演算法提示 |
| B | 看了小提示，或只查了 API / 語法後完成 |
| C | 需要先看到主要解題思路，才能完成 |
| D | 看過解法後仍然沒有完全理解 |

查詢程式語法或 API **不等於看演算法提示**。例如自己已經想到要使用 Stack，只是不知道 Python 的 `append()` / `pop()` 怎麼使用，可以查詢語法。

## 每日訓練流程

1. 先自己嘗試解題。
2. 卡住時不要立刻搜尋完整 Solution。
3. 做完後記錄「卡在哪裡」以及「這題真正的關鍵想法」。
4. 幾天後重新做不熟的題目。
5. 練習把解題思路說出口，模擬真正的面試情境。

## Hint 規則

Hint 不只看「總共做了多久」，更重要的是看自己是否已經**停止產生新的理解或進展**。

### 什麼時候可以繼續自己做

如果仍然有明顯進展，就算已經做超過一般 Hint checkpoint，也可以繼續。例如：

- 剛找到新的反例。
- 剛定位出 bug 發生在哪個條件。
- 原本的方法有問題，但已經想到新的修正方向。
- 已經確定演算法正確，目前只是 implementation / debugging。
- 可以清楚說出「我現在比 10 分鐘前多理解了什麼」。

這種情況不需要因為時間到了就強制拿 Hint。

### 什麼時候應該問 Hint

如果**連續約 8～10 分鐘沒有新的理解或有效進展**，就應該考慮問 Hint，而不是持續原地 patch。

典型訊號：

- 一直修改相似的 `if / elif`，但沒有新的 reasoning。
- 修好一個 testcase，另一個 testcase 又壞掉。
- 已經無法用一句話解釋「為什麼目前的方法對所有 input 都應該成立」。
- 發現反例其實直接推翻核心想法，卻還在硬補特例。
- 一直測試，但最近 8～10 分鐘沒有得到新的資訊。

### 完全沒有方向時的 checkpoint

- **Easy**：約 10～15 分鐘完全沒有方向，可問 Hint 1。
- **Medium**：約 15～20 分鐘完全沒有方向，可問 Hint 1。
- **Hard**：約 20 分鐘完全沒有方向，可問 Hint 1。

Hint 1 後要保留足夠時間自行消化，不要只過 5 分鐘就立刻要求 Hint 2。

### 建議硬上限

即使一直有一些小進展，也避免單題無限延長：

| 難度 | 建議硬上限 |
|---|---:|
| Easy | 30～35 分鐘 |
| Medium | 45～50 分鐘 |
| Hard | 約 60 分鐘 |

到硬上限仍未完成時，應停止單純硬磨，改為取得提示／分析核心問題，之後將題目列入複習。

### 問 Hint 時的方式

如果已經開始寫程式，**盡量把目前的 code 一起貼出來**，並說明：

- 目前做到幾分鐘。
- 現在的核心想法是什麼。
- 哪個 testcase / bug 卡住。
- 自己懷疑問題在哪裡。
- 明確要求「Hint 1，不要直接給完整解法」。

這樣可以先判斷目前卡的是：

- 演算法方向錯誤
- 缺一個 observation
- 正確演算法但 implementation 有 bug
- 複雜度還能改善
- 正在 patch 一個本質上不成立的方法

Hint 應盡量只補目前缺少的那一步，而不是直接揭露完整解法。

## 解題時間紀錄規則

除了最後 Accepted 的總時間外，之後盡量額外記錄重要時間點，方便區分問題到底出在 **pattern recognition / algorithm design**，還是 **implementation / debugging**。

建議記錄：

- **Idea time**：第一次形成可實作的主要解題方向的時間。
- **Hint time**：第一次／第二次要求 Hint 的時間，例如 `H1 18:20`、`H2 31:10`。
- **Accepted time**：最終通過全部測試的總時間。
- 如果有明顯轉折，也可以補記，例如「22:00 發現原方法被反例推翻」。

範例：

```text
152. Maximum Product Subarray
Idea: 7:40
H1: 24:10
核心 recurrence 想出: 30:30
Accepted: 43:23
```

如果一開始很快就有想法，但之後長時間 debug，也要照實記錄，不要只用總時間判斷解題能力。

例如：

```text
Idea: 5:00
第一個 bug: 12:00
找到新的修正方向: 22:00
連續約 10 分鐘沒有新進展 -> 詢問 Hint
Accepted: 40:00
```

這種情況代表前半段一直有進展，因此不必在固定的 15 或 20 分鐘強制拿 Hint；真正需要注意的是後段是否進入長時間停滯。
